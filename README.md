# Pi Voice — local-first, not deployed
Node 22+, no npm dependencies. Owner-only Pi status and follow-up messaging for an existing ElevenLabs/Twilio voice agent. Default HTTP bind **127.0.0.1:4123**; future tunnel origin **http://127.0.0.1:4123**, hostname **dev.anello.co**, tunnel **dev-voice**. No public route yet.

## Bounded send-and-wait
`/message` now waits briefly for a positively correlated visible assistant reply; timeout is normal and same-ID retries never resend. See [wait-for-reply setup and limitations](docs/wait-for-reply.md). Set the existing ElevenLabs message tool response timeout to **30 seconds**, restart the bridge, and `/reload` Pi sessions before using this behavior.

## Local setup (manual, explicit)
1. `cd /home/baxter_robots/pi-voice && npm test`
2. Copy `config.example.json` to `config.json`, `chmod 600 config.json`, privately fill values. Generate initiation secret with `openssl rand -hex 32`. Use a distinct unique spoken phrase, not an existing password. Passphrase matching ignores capitalization and Unicode punctuation in both the configured phrase and spoken candidate; whitespace must still match. Restart the bridge after changing configuration or code. Do not paste credentials into chat or shell command arguments. Use a Twilio API key permitted to read this account's calls.
3. `mkdir -m 700 run` (if absent). Bridge and opted-in agents must use the same absolute IPC directory.
4. Start bridge manually: `npm start` (or `node src/main.mjs /private/path/config.json`). No environment credential loading, services or tunnel changes are automated.
5. In a NEW disposable Pi session, explicitly opt in: `PI_VOICE_IPC_DIR=/home/baxter_robots/pi-voice/run pi -e /home/baxter_robots/pi-voice/extensions/voice.mjs`. Do not reload existing production sessions without operator approval.
6. Status automatically includes `recentMessages`: up to **8 completed user messages / visible assistant replies**, each clipped to **800 characters**, with role, original timestamp (or null), and a truncation flag. The latest active-branch messages are loaded on opt-in/resume and refreshed on branch navigation/compaction; live `message_end` events update them. Only user text and assistant `text` blocks are included: no images, hidden thinking, tool calls/arguments, tool outputs, system/custom messages, bash output, or summaries from other branches. Phone work instructions are ordinary user messages and remain included. The owner explicitly authorized sharing these excerpts with ElevenLabs. Ordinary conversation can contain sensitive information: there is **no arbitrary secret detection/redaction**. Phone passphrase exchanges stay in the bridge `/verify` flow and never enter Pi/excerpt state. Activity/tool names also update automatically. Optionally publish a concise summary with `/voice-progress Implementing onboarding; tests next`; an empty `progress` means no manual summary, not that automatic excerpts are unavailable.

Only instrumented live Pi instances are listed, including optional children if explicitly loaded. Socket instance UUID is the exact message target; Pi session ID/name and TMUX_PANE are labels. No tmux keystrokes or arbitrary shell/start/stop/approval API exists.

## Future ElevenLabs configuration — gate before routing
First review `docs/provider-binding.md` and perform a controlled end-to-end test. A local test with mocked provider metadata is NOT proof of live provider security.

- Configure inbound conversation initiation webhook POST `https://dev.anello.co/initiate`, header `x-init-secret` from a workspace secret. It must NOT be attached to tools. Turn on fetching initiation data for inbound Twilio calls. Preserve the current phone integration.
- Register `secret__pi_voice` as a secret dynamic variable, returned by initiation. No valid default in previews. Bind each tool's **dynamic header** `x-pi-voice` to `{{secret__pi_voice}}`. Never make this a model parameter, prompt variable, or ordinary tool response.
- All tools POST JSON: `/verify` `{ "passphrase": "spoken candidate" }`; `/list` `{}`; `/status` `{ "instance": "UUID from list" }`; `/message` `{ "instance": "UUID", "id": "stable-request-id", "text": "instruction" }`.
- Verification must precede every read/message; the backend enforces this irrespective of prompting. Agent should ask for phrase, never repeat it, never claim access on failed verification, resolve ambiguous names, and never claim a submitted message was ingested, queued, or acted upon without separate evidence.
- On transient message errors keep the SAME message ID and payload. Never retry automatically with a new ID. Ledger retains up to 1000 IDs per extension process, then refuses new IDs. It survives bridge restart but not Pi restart; process instance changes then. A normal void return from public `sendUserMessage` produces **`submitted_unconfirmed`**, with `acted:false`: this confirms only submission to the public API, **not ingestion, acceptance, queuing, execution, or completion**. Installed Pi catches asynchronous delivery failures separately, so even a later rejection leaves this receipt unconfirmed. A synchronous exception leaves `indeterminate`, also with `acted:false`. Both states remain deduplicated; retrying the same ID retrieves the same receipt without resubmission. The wait extension can subsequently report `response_observed` only with matching user-envelope ingestion and a successful visible assistant turn; otherwise submission remains unconfirmed. See docs/wait-for-reply.md. Never tell the caller an instruction was accepted or queued based on these receipts. All submissions explicitly set `deliverAs:'followUp'`, even when initially idle, avoiding idle-to-busy races across asynchronous input hooks.
- Initiation keeps 100 call records/tombstones per bridge lifetime, then fails closed. Restart manually to clear records (revokes all authorizations). Expired/locked replay cannot refresh lifetime/attempts. Up to 3 bad phrases per call, 10 globally per 15-minute window. No logs contain request bodies or passphrases; HTTP errors are generic.
- Status freshness is 30 seconds since heartbeat (5-second heartbeat). Excerpt timestamps indicate when those messages were written; a healthy heartbeat does not make old conversation new. IPC status responses are capped at 64 KiB, including worst-case JSON-escaped excerpt text. Unreachable sockets are marked stale. Stale targets reject new delivery. Cleanup old socket files manually only after confirming those processes exited; discovery considers at most 100 socket files.

## Publication checks
Before adding dev.anello.co route, validate provider trust assumptions, nonowner rejection, wrong phrase/lockout, missing capability, model-forged identity, ended call, expiry, duplicate delivery, stale process, and failure of Twilio lookup. Tests cover these with mocks; live configuration remains manual. Stop immediately if dynamic-header isolation or call binding cannot be demonstrated.

Then, and only with operator approval, publish dev.anello.co to `http://127.0.0.1:4123` using dev-voice. Do not expose the IPC directory, SSH, or other local ports. Do not use an interactive Cloudflare Access login on tool endpoints; it is not the call authorization mechanism. Keep bridge auth even behind Cloudflare. Rollback: remove published route, stop bridge, shut down opted-in test sessions; no system/global files have been installed.
