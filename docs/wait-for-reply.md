# Existing /message now waits for a correlated reply

No tool body changes: POST `/message` still takes `instance`, `id`, `text`.

## Provider configuration and rollout
Reviewed current ElevenLabs create-tool reference, webhook section:
https://elevenlabs.io/docs/eleven-agents/api-reference/tools/create.md
It documents `response_timeout_secs` default **20**, webhook range **5–300 seconds** (client tools have a different range). Set the existing send_workstream_message webhook tool **response timeout to 30 seconds**. Keep execution mode **immediate** (blocking); optionally enable pre-tool speech and a tool-call sound. No enterprise monitoring or additional tool required. Keep dynamic x-pi-voice header bound to secret__pi_voice and all existing authentication settings.

Change tool description/instructions to: 'Submit the caller’s instruction, then wait briefly for a correlated visible reply. Read response.text if present. wait:timed_out means no correlated reply was observed yet, not that delivery failed or nothing happened. Check again with EXACTLY the same instance, id and text; never create a new ID to retry. Unconfirmed submission does not prove acceptance. Do not infer a reply from unrelated recent output.'

Operator must restart bridge (Ctrl+C, then npm start from project directory), and run `/reload` in each Pi session to install the updated lifecycle handlers. Do not launch a duplicate explicit extension when the global wrapper is loaded. Instance UUIDs change on reload: list workstreams again. Never automatically replay old instructions against a new instance/ID because the old instance may already have acted. No service, tunnel or live process was changed by implementation.

## Timing and transport
The bridge polls the existing short IPC message operation every 250 ms for an **8-second window** measured with monotonic `performance.now()` (wall-clock changes do not extend it), with the existing **2-second IPC timeout** per request. This preserves deduplication: every poll has identical ID/text and looks up the existing ledger entry; it never resubmits. A final IPC operation can extend waiting to roughly 10 seconds. Initial and final Twilio authorization lookups each have a 4-second deadline, leaving headroom within the 30-second webhook setting. The HTTP inactivity timeout is 30 seconds; request upload/header deadlines remain 10 seconds. IPC itself never holds a request waiting for a model.

The HTTP response close aborts the polling timer; an already-running IPC operation may take up to its 2-second deadline to finish. Disconnect does not cancel an instruction already submitted. No background waiter or IPC subscription survives the HTTP request. Up to 32 HTTP connections remains the existing bound. Ended/expired calls or provider failures fail closed at final authorization before releasing either a reply or timeout receipt. An end immediately after the last Twilio lookup remains the preexisting non-atomic provider race.

## Response and correlation semantics
A response uses the original receipt fields plus `wait:reply` and `response:{role,text,timestamp,truncated}`; the receipt is `response_observed`. At most 800 characters of visible assistant text are returned. Tool arguments/calls/results, hidden reasoning and images are excluded. `acted:false` deliberately does not assert the requested work is complete.

With no attributable reply, return `wait:timed_out` and the existing `submitted_unconfirmed` or `indeterminate` receipt. Same-ID retries can observe a later reply without submitting again. Reusing an ID with different text fails. The bounded 1000-ID in-process ledger and stale-heartbeat rejection remain unchanged.

Each submission gets an unpredictable envelope nonce; only an exact user message_end containing that full envelope establishes ingestion. Assistant turn_end must report successful stop with no tool calls and visible text after that ingestion. At each turn boundary the candidate's full expected envelope is rechecked against `event.context.contextMessages`, the installed Pi runner's projected boundary context: it must occur exactly once and be the latest projected user message. A later message_end replacement, missing projection, or intervening projected user input drops attribution. Tests exercise the installed runner replacement chain and in-memory SessionManager projection; this does not establish guarantees about arbitrary later boundary/context/model-provider mutations. Preexisting output alone cannot complete a phone request. Multiple user messages before a successful assistant turn are ambiguous (including concurrent phone instructions or steering); attribution is dropped rather than guessing. Tool-use turns retain attribution until a successful final visible turn; errors, aborts, length termination and unknown outcomes invalidate it. Branch navigation/compaction drops pending correlation; shutdown/session replacement closes the old instance and loses its ledger. These conservative cases may time out despite actual execution. Extension input transforms that alter the envelope also prevent correlation. This is observed conversational sequencing, not a model-level guarantee that the reply semantically answers the instruction.

Recent conversation excerpts, spoken-passphrase normalization, authentication and ordinary status endpoints are unchanged. Old extension versions continue to accept instructions but cannot report correlated responses, so they time out until reloaded.
